# bunnybearbeads

## Данные товаров

### Где лежат

База изделий — в Dropbox: `~/Library/CloudStorage/Dropbox/bunnybearbeads` (папка всегда доступна офлайн). В проекте это симлинк `data/` (в `.gitignore`):

```sh
ln -s ~/Library/CloudStorage/Dropbox/bunnybearbeads data
```

Одно изделие — одна папка, всё про него лежит там:

```
data/
  2026-10-22 Solar Flare/       ← имя папки для себя: дата в начале — сортировка в Finder и Windows
    product.json                ← данные сайта, штуки, memo, даты — всё про изделие
    site/PB090071.jpg           ← фото и видео для сайта (готовые, нужного размера)
    …                           ← что угодно ещё: процесс, схемы, черновики
  _families/cats.json           ← семейства; папки с «_» в начале — служебные
```

Сайт берёт из базы только изделия с `"site": true` и только файлы, указанные в их `product.json`. Генерирует `scripts/export-data.mjs` (сам при `npm run dev` и `npm run build`, в dev ещё и следит за `data/`; вручную — `npm run export-data`):
- `src/content/products/<slug>.json` и `src/content/families/<id>.json`;
- `public/images/products/<slug>/…` — копии указанных фото и видео, плюс постеры к видео.

Всё сгенерированное — в `.gitignore`. Наружу уходит только количество непроданных штук по точкам и комментарии к точкам с фото; `maker`, `id`, `createdAt`, `soldAt`, `memo` и проданные штуки на сайт не попадают.

**Любая проблема в базе роняет сборку** со списком всего, что надо поправить: битый JSON, конфликтная копия Dropbox (в имени «conflicted copy»), файл не найден или «только онлайн», путь за пределы папки изделия, дубль slug или id штуки, неизвестная точка, семейство ссылается на товар не с сайта. Папка без `product.json` пропускается с предупреждением.

### Изделие — `<папка>/product.json`

- `slug` — адрес страницы `/catalog/<slug>`: латиница в нижнем регистре, цифры, дефисы. Уникален по всей базе. Папку можно переименовывать — адрес не изменится.
- `site` — `true` / `false`: показывать ли на сайте. Подарки, прототипы, незаконченное — `false`.
- `maker` — `bunny` / `bear`: кто сплёл. На сайт пока не выводится.
- `images`, `thumb`, фото в `locationNotes` — пути **относительно папки изделия**: `"site/PB090071.jpg"`, видео — `{ "type": "video", "src": "site/turn.mp4" }`. Постер видео делается сам (кадр через ffmpeg), свой — полем `poster`.
- `thumb` — превью 40:22 для плашки в семействе. Без него — `placeholder-thumb.svg`.
- `locationNotes` — комментарий для посетителей к штукам в точке: `{ "ngay-mai": { "note": {en, ru, vi}, "images": [...] } }`. Один на точку: если штуки в точке разные, так и пишем словами («у меня две версии: одна такая, другая такая»). Показывается в «Наличии» под количеством, фото открываются галереей. Если в точке нет непроданных штук, комментарий не выводится (экспорт предупредит).
- `items` — физические штуки, по одной записи на штуку:

| Поле | Что это |
|---|---|
| `id` | Уникальный на всю базу (включая `site: false`), например `BB-0042` |
| `location` | `dalat`, `ngay-mai`, `cat-food` |
| `createdAt` | Когда сделана |
| `soldAt` | Когда продана. Проданную штуку не удаляем, ставим дату |
| `memo` | Для себя: история создания и т. п. На сайт не попадает |

Нет непроданных штук в Далате — на сайте предлагается повтор, это обычный путь заказа.

Код NGÀY MAI в данных не храним: он определяется по цене (`getNgayMaiCategory`).

### Семейство — `data/_families/<id>.json`

Товары, которые показываются плашками-ссылками под галереей на странице каждого из них.

- `title` — заголовок над плашками, обязателен, с переводами.
- `members` — товары по порядку, не меньше двух. У каждого необязательный `note` — чем отличается, два-три слова («Крупный бисер»): выводится в плашке после цены.
- Только товары с `"site": true`. Товар состоит не больше чем в одном семействе — иначе сборка падает.

### Уровни различий

Названия в скобках — только для нас, чтобы не перепутать предметы. На сайт и в данные они не попадают.

## Сборка и публикация

Сайт собирается только на этом компьютере: база изделий в Dropbox видна только здесь. GitHub Actions сайт не собирает.

- `npm run build` — сборка в `dist/`. В конце — размер сборки, из чего она состоит, прирост с прошлой сборки и самые тяжёлые файлы. Лимиты GitHub Pages: сайт до 1 ГБ (предупреждение с 80%), файл до 100 МБ.
- `npm run deploy` — сборка и публикация: `dist/` уходит в ветку `gh-pages` одним коммитом с force push, история ветки не копится. Незакоммиченный код тоже публикуется (с предупреждением), в сообщении коммита — хеш исходного коммита.
- GitHub: Settings → Pages → Build and deployment → Source: **Deploy from a branch**, ветка `gh-pages`, папка `/ (root)`.
- `public/CNAME` — домен. Без него при публикации из ветки GitHub сбросит свой домен.

### Новый компьютер

Всё ценное живёт не на компьютере: код — на GitHub, база изделий — в Dropbox, номер Zalo — в менеджере паролей.

1. Dropbox: войти, папку `bunnybearbeads` сделать доступной офлайн, дождаться синхронизации.
2. Node 22+ и git; `git clone https://github.com/bunnybearbeads/bunnybearbeads.git`, в папке — `npm ci`.
3. Симлинк на базу: `ln -s ~/Library/CloudStorage/Dropbox/bunnybearbeads data`.
4. `.env` с `ZALO_PHONE=84…` (см. «Как спрятан номер Zalo» в TODO.md).
5. Вход в GitHub для `git push` (например, `gh auth login` или ключ SSH).
6. `npm run build` — проверить, что собирается; `npm run deploy` — опубликовать.

## QR-коды в модалках заказа

Лежат в `public/images/qr/` (`telegram.svg`, `messenger.svg`, `zalo.svg`), выводятся в `src/components/QrModal/`.

Генерируем здесь: https://www.nayuki.io/page/qr-code-generator-library

1. **Text** — полная ссылка с `https://`, например `https://m.me/bunnybearbeads`.
2. **Error correction** — Quartile.
3. **Output format** — Vector.
4. **Border** — 0.
5. Остальное не менять. Скачать SVG и положить в `public/images/qr/`.

После скачивания открыть SVG в редакторе:

- **Обязательно удалить белый фон** — строку `<rect width="100%" height="100%" fill="#FFFFFF"/>`. QR в модалке работает как маска: градиентом закрашивается всё непрозрачное, и с фоном вместо кода получится сплошной цветной квадрат.
- В тег `<svg>` добавить `width="500" height="500" shape-rendering="crispEdges"` — размер как у остальных и чёткие края клеток.

Проверить телефоном прямо из модалки на сайте, а не из самого файла: в файле код читается и с фоном.

## Большие скругления

При радиусе от 28px добавлять `corner-shape: superellipse(1.3);`:

```css
border-radius: 44px;
corner-shape: superellipse(1.3);
```

- Чтобы угол выглядел так же, как обычный круглый, радиус увеличить примерно в 1,2 раза (37px → 44px).
- При радиусах 12–16px разницы не видно — не добавлять. Кнопки, «пилюли» и круги не трогать.
- На мобильном (`width < 740px`) радиус меньше: у `.window` 28px вместо 44px.
- `@supports` не нужен: где поддержки нет, будет обычный круглый угол.

## Правила CSS

- **Цвета:** `rgb(255 255 255 / 90%)`, а не `rgba(255, 255, 255, 0.9)`; так же `hsl(h s% l% / a)`, а не `hsla()`.
- **Прозрачность** в процентах: `opacity: 80%`, а не `0.8`.
- **Медиазапросы** диапазонами: `@media (1600px <= width)`, `@media (width < 740px)`, `@media (740px <= width < 1200px)` вместо `min-width` / `max-width`.
- **Трансформации и раскладка:** где уместно — отдельные `translate`, `rotate`, `scale`, а также subgrid и логические свойства.
- **Переходы при наведении:** `var(--transition-hover)`, а не `0.2s ease`.

### Мониторы (`1600px <= width`)

Сайт не увеличиваем как при зуме: единого коэффициента нет, у разных свойств он свой.

| Что | Примерно |
|---|---|
| Шрифты, `line-height`, иконки | ×1,1–1,15 |
| Ширины, картинки, кнопки | ×1,13–1,2 |
| Отступы (`padding`, `margin`, `gap`) | ×1,2–1,3 |

- Это ориентир по уже свёрстанным компонентам, а не формула: итог подбираем на глаз. Размеры целые.
- Учитываем форму экрана: мониторы бывают и вытянутые, и невысокие (1600×800), поэтому высоту увеличиваем осторожнее ширины.
- Стили для мониторов — блоком `@media (1600px <= width)` в конце файла компонента.
