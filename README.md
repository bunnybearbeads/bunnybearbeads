# bunnybearbeads

## Данные товаров

### Где лежат

База изделий — в Dropbox: `~/Library/CloudStorage/Dropbox/bunnybearbeads` (папка всегда доступна офлайн). В проекте это симлинк `data/` (в `.gitignore`):

```sh
ln -s ~/Library/CloudStorage/Dropbox/bunnybearbeads data
```

Одно изделие — одна папка, всё про него лежит там:

```
data/
  Lumi/                         ← имя папки — для себя, обычно название изделия
    Lumi.json                   ← данные изделия, называется как папка: сайт, штуки, privateNote, даты
    site/PB090071.jpg           ← фото и видео для сайта (готовые, нужного размера)
    …                           ← что угодно ещё: процесс, схемы, черновики
  _thumbs/Lumi.png              ← thumb изделия: называется как папка (см. «thumb» ниже)
  _system/                      ← всё служебное; папки с «_» в начале — не изделия
    families/aura-morpho.json   ← семейства
    product.schema.json         ← подсказки для редактора (см. ниже), генерируются
    family.schema.json
    dates.txt                   ← заметки для себя, сборка не читает
    demo/                       ← демо-база той же структуры (со своей _system), на сайт не попадает
```

**Демо-база** `data/_system/demo/` — вымышленные изделия (Happy Paws, Bowtie Cat, Sunburst…) со сложными случаями: много штук в разных точках, проданные, подаренные, неполные даты, двойняшки, ремейк, комментарии с фото, семейства. Образец, как что записывать, и стенд для вёрстки. `npm run dev:demo` — dev-сервер на демо-базе вместо настоящей (обратно — `npm run dev:restart`). Опубликовать демо нельзя: `npm run deploy` с `DATA_DEMO` откажется.

Сайт берёт из базы только изделия с `"site": true` и только файлы, указанные в их JSON. Генерирует `scripts/export-data.mjs` (сам при `npm run dev` и `npm run build`, в dev ещё и следит за `data/`; вручную — `npm run export-data`):
- `src/content/products/<slug>.json` и `src/content/families/<id>.json`;
- `public/images/products/<slug>/…` — сжатые копии фото (см. «Фото» ниже), копии видео и постеры к ним.

Всё сгенерированное — в `.gitignore`. Наружу уходят только количество и цена штук в наличии по точкам, цена в шапке, статус и цена ремейка, комментарии к точкам с фото; `id`, `maker`, даты, `out`, `privateNote`, `remake.privateNote` и ушедшие штуки на сайт не попадают.

Комментарии в базе названы по тому, кто их видит: `publicNote` и `publicNoteImages` — посетители сайта, `privateNote` — только вы. Старые имена (`note`, `noteImages`, `memo`) роняют сборку с подсказкой.

**Любая проблема в базе роняет сборку** со списком всего, что надо поправить: битый JSON, конфликтная копия Dropbox (в имени «conflicted copy»), старые поля `images` (теперь `gallery`), `thumb` (теперь папка `_thumbs`), `designer`/`designedBy` у изделия (теперь `credits.designer`), старые роли `craft`/`design`/`photo` в `credits` (теперь `crafter`/`designer`/`photographer`; `maker` в `credits` — тоже старое, теперь `crafter`) и `materials` у изделия (теперь у штук), файл не найден или «только онлайн», путь за пределы папки изделия, дубль slug, названия (без учёта регистра) или id штуки, id не по формату, неизвестная точка или категория, брелок без `attachTo`, штука без цены или с неверным `out`, изделие на сайте без фото, с фото не 3:4, без thumb или с thumb не 40:22, неверный или лишний `remake`, семейство ссылается на неизвестный товар. JSON изделия называется как папка (`Lumi/Lumi.json`): переименовали папку — переименуйте и JSON, иначе сборка упадёт. Папка совсем без JSON пропускается с предупреждением.

### Изделие — `<Папка>/<Папка>.json`

**Обязательно у изделий с `"site": true`:** `description`, `gallery` (хотя бы одно фото), `size` у штук (вместе с `weight` внутри), `credits` (с `crafter` и `designer`) — без них сборка упадёт. У скрытых (`"site": false`) всё это можно заполнить потом.

**В JSON всегда все поля** — пустые тоже, чтобы было видно, куда что вписать: `""`, `{ "en": "", "ru": "", "vi": "" }` (пустой перевод — одной строкой), `[]` (фото — пути через запятую). У `locationNotes` — только заполненные точки, а если их нет — одна пустышка `atelier`: скопировать и поменять ключ на нужную точку. Пустое значение — то же, что отсутствие поля: обязательность полей от этого не меняется. Наполовину заполненный перевод (`ru` есть, `en` пустой) — ошибка сборки. `npm run fill-data` дописывает недостающие пустые поля во все изделия и семейства и выстраивает их в одном порядке, заполненное не трогает — удобно после добавления нового изделия.

**Подсказки в редакторе.** Первая строка каждого JSON — `"$schema": "../_system/product.schema.json"` (у семейств — `../family.schema.json`). По ней редактор (VS Code, WebStorm, Zed) по Ctrl+Пробел показывает, какие поля бывают и какие у поля допустимые значения (`attachTo`: `keys`, `phone`, `mirror`, `bag`; `location`, `category`, `maker`, `out.type`; в семействе — slug изделий), при наведении — описание поля, а опечатки и цену в кавычках подчёркивает сразу. Схемы лежат в `_system` (в демо-базе — свои), генерирует их `npm run fill-data` из списков в `scripts/data-rules.mjs` — из тех же, по которым проверяет сборка; руками не править. Добавили точку, категорию или изделие — `npm run fill-data`, иначе сборка предупредит, что подсказки устарели. Схема — только подсказка: правила вроде «`attachTo` только у брелков» проверяет сборка.

- `order` — место в каталоге, необязательно: число без кавычек (`3`, не `"3"`), меньше — выше. Без `order` изделие уходит в конец; при одинаковом `order` (или когда его нет) — по алфавиту `title`. Числа не обязаны идти подряд: удобно ставить с шагом 10, чтобы потом вставлять между.
- `slug` — адрес страницы `/catalog/<slug>`: латиница в нижнем регистре, цифры, дефисы. Уникален по всей базе. Папку можно переименовывать — адрес не изменится.
- `title` — название, всегда по-английски, одной строкой: не переводится.
- `category` — что это за изделие, в единственном числе (кроме `earrings`: серьги — пара): `charm`, `bracelet`, `ring`, `earrings`, `pen-wrap`. Брелки на телефон, ключи и сумку — одна категория `charm`: застёжка меняется, на что носится конкретная штука — в её `attachTo`. Разделы каталога на сайте задаются в `src/config/categories.ts`: сейчас серьги и обмотки для ручек показываются в «Разном»; наберётся достаточно — дать им свой раздел там, данные не трогать.
- `description` — описание, одна строка по-английски, как `title`: переводов пока нет.
- `description`, `publicNote` в `locationNotes` и `remake.publicNote` — один абзац без `<p>`, `<div>` и других блочных тегов (сборка упадёт); обёртку даёт сайт. Строчные теги можно: `<strong>`, `<em>`, `<a>`, `<br>`. В карточке каталога теги описания вырезаются, остаётся текст.
- `size` — **у штуки** (`items`), как материалы: у разных штук размер может быть разный. Размер и вес одним объектом, поля по категории (`npm run fill-data` вписывает нужные, редактор подсказывает по `category`). Числа без кавычек, можно дробные (`1.2`): длины — в сантиметрах, `weight` — в граммах. Подписи, единицы и запятую в дробях («1,2 см») ставит сайт (`src/utils/size.ts`), каждое значение — отдельной строкой, вес — последней:
  - браслет — `width`, `length`, `weight`. «На запястье от» сайт считает сам: длина / 1,1, с округлением до 0,5 см;
  - брелок — `width`, `height` (без крепления), `weight`: «2,5 × 3 см без учёта крепления»;
  - кольцо — `beads` (ширина в бисеринах), `fingerFrom`/`fingerTo` (обхват пальца), `sizeFrom`/`sizeTo` (размер; один — как `sizeFrom`), `weight`;
  - серьги и обмотки для ручек — `width`, `length`, `weight`.
  На сайте — размер той же штуки, что и материалы: последней в наличии, а если в наличии ничего нет — последней с заполненным размером. У браслетов и колец главное о размере выводится ещё и в шапке товара, рядом с ценой («На запястье от 91 см», «Размер кольца 17»). Если у штуки в наличии размер другой (вес не в счёт), у её точки обязателен комментарий для посетителей (`locationNotes`), иначе сборка упадёт — как со «штуками с комментарием» ниже.
  Пустые поля не выводятся. Заголовок секции — «Размер и вес» (или только «Размер» / «Вес»). Поля — `SIZE_FIELDS` в `scripts/data-rules.mjs`.
- `credits` — кто сделал, просто имена текстом, без HTML: `crafter` — кто сплёл, имя на сайте (`bunnybearbeads` или `tonybrickstitch`; не путать с `maker` у штуки) и `designer` — автор схемы обязательны; остальные роли — по желанию и любые: `photographer` — автор фото (подпись Photo by), можно добавить автора видео, соавтора и т. п. На странице выводятся все пары: сначала crafter, потом designer, остальные — по порядку в JSON; у crafter, designer и photographer подписи переведены, у других ролей подпись — сам ключ с заглавной буквы (`"video": "Mai"` → «Video: Mai»). Нет `credits`, `designer` или `crafter`, или в имени HTML — сборка упадёт; старые `designer`/`designedBy` — тоже. Если все имена — bunnybearbeads, секции Credits на странице нет.
- Материалы — не у изделия, а у каждой штуки (`items[].materials`, см. ниже).
- `site` — `true` / `false`: показывать ли на сайте. С `true` обязательно хотя бы одно фото в `gallery` (заглушки нет — сборка упадёт). Временные демо-фото называются `site/temp-*.jpg`: заменить настоящими. Подарки, прототипы, незаконченное — `false`.
- `gallery` (фото и видео изделия, первое — обложка в каталоге), `publicNoteImages` (фото к комментариям) — пути **относительно папки изделия**: `"site/PB090071.jpg"`, видео — `{ "type": "video", "src": "site/turn.mp4" }`. Постер видео делается сам (кадр через ffmpeg), свой — полем `poster`.
- Фото в `gallery` — **строго 3:4, вертикальные** (1440×1920, 3024×4032…), без допуска: ширина делится на 3, высота на 4, и частные равны. Редакторы при кропе часто округляют (2213×2952) — такое сборка не пропустит и подскажет точный размер (2211×2948). Иначе сборка упадёт и подскажет, до какого размера обрезать. Поворот из EXIF учитывается — снятое на телефон вертикально проходит. Проверяются только изделия с `"site": true`; видео и `publicNoteImages` не проверяются.

### Фото

В базу кладём **оригиналы**: готовые обработанные JPEG в полном размере (4K — нормально), без уменьшения и пересжатия. PNG и TIFF тоже можно; RAW и HEIC — нет, сборка скажет, что не может прочитать файл.

Экспорт (`scripts/photos.mjs`) сам делает из каждого фото копии для сайта:
- всего две копии: **180×240** (small — миниатюры галереи, фото к комментариям) и **1080×1440** (large — галерея на странице, лайтбокс, карточка каталога). Больше оригинала не растягивает. thumb семейства — одна копия **160×88** (плашка 80×44 × 2 для Retina);
- **JPEG** (mozjpeg) с сильным сжатием — **качество 50**, обе копии под Retina. На Retina сжатие не заметно, обычный экран получает тот же файл, уменьшенный вдвое, — артефакты сглаживаются. Выбора размера браузером (`srcset`) нет: у каждого места свой файл (компонент `src/components/Photo/Photo.astro`). AVIF не используем: он требует запасного JPEG — файлов вдвое больше;
- цель — экономия: 500 изделий с видео должны влезть в лимит GitHub Pages (1 ГБ);
- EXIF, в том числе GPS с телефона, в копии не попадает. Видео копируется без пережатия, но тоже без метаданных (геолокация, модель телефона, дата): ffmpeg оставляет только картинку и звук.

Пример: в среднем по нашим фото 1080 — ~160 КБ, 180 — ~7 КБ, то есть ~170 КБ на фото (было ~1,5 МБ на четыре копии с качеством 80).

Сжатие — около секунды на фото 4K, делается один раз: дальше пересжимается только изменённый оригинал (кэш — `node_modules/.cache/bunnybearbeads/photos.json`). Поменяли ширины или качество в `scripts/photos.mjs` — пересожмутся все фото.
- **thumb** — превью 40:22 для плашки семейства (больше нигде не показывается). Поля в JSON нет: все thumb лежат одной папкой `_thumbs` в корне базы — удобно экспортировать из Фигмы пачкой и переэкспортировать с заменой. Файл называется как папка изделия: `Lumi/` → `_thumbs/Lumi.png` (можно `.jpg`). Регистр не важен, `_` и `:` считаются одинаковыми — Фигма заменяет двоеточие: «Sunlit Orchard_ Early Pick.png» подойдёт к папке «Sunlit Orchard: Early Pick». Размер — **строго 40:22** (240×132 из Фигмы — нормально: на сайт уходит уменьшенная копия 160×88, плашка — 80×44), иначе сборка упадёт и подскажет кроп. У изделия с `"site": true` thumb обязателен: нет файла — сборка падает. Лишние файлы (изделий ещё нет в базе) не мешают; на сайт копия уходит под именем `<slug>/thumb`, так что имя файла наружу не попадает. В демо-базе — своя `_thumbs` (кадры из галереи). Старое поле `thumb` в JSON — ошибка сборки.
- `locationNotes` — комментарий для посетителей к штукам в точке: `{ "ngay-mai": { "publicNote": {en, ru, vi}, "publicNoteImages": [...] } }`. Один на точку: если штуки в точке разные, так и пишем словами («у меня две версии: одна такая, другая такая»). Показывается в «Наличии» под количеством, фото открываются галереей. Если в точке нет штук в наличии, комментарий не выводится (экспорт предупредит).
- Своих даты, цены и мастера у изделия нет — всё это у штук. Понадобится сортировка по возрасту — по самой ранней штуке.
- `remake` — необязательные настройки ремейка. Ремейк сайт предлагает всегда, когда в Далате нет ни одной штуки: все заказы и доставка по Вьетнаму — из Далата, партнёры ничего не отправляют. Материалы считаем всегда доступными (бисер — полными банками); если что-то не так — пишем в `publicNote`, остальное решается в мессенджере. Пока штука в Далате есть, `remake` должен быть пустым — сборка упадёт:

| Поле | Что это |
|---|---|
| `price` | Цена ремейка. Обязательна, когда в наличии нет ни одной штуки; если штуки где-то есть — необязательна и должна совпадать с их ценой (см. «Цена» ниже) |
| `publicNote`, `publicNoteImages` | Комментарий для посетителей, как у точки: «оригинального бисера нет, могу заказать или заменить на похожий». Выводится в карточке мастерской под кнопкой ремейка, фото — галереей |
| `privateNote` | Для себя. На сайт не попадает |

- `items` — физические штуки, по одной записи на штуку, хотя бы одна обязательно. Ушедшие штуки не удаляем, а пишем им исход `out`:

| Поле | Что это |
|---|---|
| `id` | 3–4 заглавные буквы и две цифры по порядку, без тире: `PWST01`, `PWST02`… Буквы — первые согласные названия (`PWST` — Pawsitivity), у всех штук изделия одинаковые; сборка этого не проверяет, только формат и уникальность id по всей базе. Номер ушедшей штуки не переиспользуется. Одна штука — один id, даже если штуки неотличимы (пример в демо — двойняшки HPPW11 и HPPW12 в Happy Paws) |
| `maker` | Кто сплёл: `bunny` / `bear`. Обязательно, на сайт не выводится. Если не сказано иное — `bunny`: плетёт большинство |
| `price` | Цена, по которой штука выставлена, в донгах. Обязательно, остаётся и после ухода — в отчётах это стоимость штуки |
| `attachTo` | Только у брелков (`category: charm`), и там обязательно: на что сделана штука — `keys`, `phone`, `mirror`, `bag`. У остальных категорий поля нет. Одно изделие может быть сделано в разных вариантах ношения |
| `materials` | Материалы штуки — разобранные: бисер по типам с кодами цветов, HTML собирает сайт (см. «Материалы» ниже). У каждой штуки свои: бисер мог закончиться, застёжка поменяться. Сайт показывает материалы одной штуки — последней в наличии (по порядку в `items`), а если в наличии ничего нет — последней в списке с заполненными материалами: ремейк делается как она. Одинаковые у всех штук — просто скопировать |
| `location` | `atelier` (своя мастерская, сейчас в Далате — id без города на случай переезда), `ngay-mai`, `cat-food` |
| `craftedAt` | Когда сплетена. Обязательно. Можно неполную дату (см. «Даты» ниже) |
| `consignedAt` | Когда отдали партнёру на консигнацию. Есть только у штук у партнёров (`ngay-mai`, `cat-food`), и там обязательно — нужно для накладных. У штук в `atelier` поля нет. Можно неполную дату |
| `out` | Исход, если штука ушла. Нет `out` — штука в наличии в своей `location` |
| `privateNote` | Для себя: история создания и т. п. На сайт не попадает |

**Материалы:**

```json
"materials": {
  "beads": {
    "Miyuki Delica 11/0": [877, 1494, "PF557"],
    "Toho Aiko": []
  },
  "additionalBeads": {
    "Basic beads": ["pale"],
    "Unbranded bicones": ["crystal"]
  },
  "threads": {
    "FireLine": ["Smoke"]
  },
  "findings": "Basic keyring"
}
```

- `beads` — тип бисера → коды цветов как на упаковке: числа или строки (`"402B"`, `"DBS-10"`, `"#426"`). Цвета неизвестны — `[]`. Типы — только из списка `BEAD_TYPES` в `scripts/data-rules.mjs` (редактор подсказывает по Ctrl+Пробел); Delica 11/0 и 10/0 — разные типы. Новый бисер — дописать туда и `npm run fill-data`.
- На сайте: один цвет — код в названии (`Miyuki Rocailles 11/0 #426`), несколько — строка «Colors: …». Ровно два бисера — одной строкой: у обоих по одному цвету — коды в названиях («6mm Miyuki Bugles #401 & Miyuki Rocailles 11/0 #194»), хотя бы у одного несколько — короткие названия и цвета всех строкой ниже («Miyuki Delica & Toho Aiko», «Delica colors: 2113 · Aiko colors: 41, 42»), три и больше — по пункту на каждый. Приписка «high-quality Japanese seed beads», с Toho Aiko — «the world’s best seed beads»; приписки переводятся (`src/i18n/ui.ts`), названия — нет. HTML собирает `src/utils/materials.ts`.
- `colorsPublic` — можно ли публиковать цвета бисера: `"yes"` — да (по умолчанию); `"no"` — нет, подбор цветов — секрет автора купленной схемы (Etsy и т. п.): цвета остаются в базе — для истории и печатной карточки покупателю, — а сборка вырезает их ещё до сайта, на странице только тип бисера и пояснение, что цвета — на карточке; `"replaced"` — да, оригинальный подбор — часть платной схемы, но бисер заменён своим: цвета выводятся и пояснение, что микс свой. Тип бисера не секрет.
- `additionalBeads` — бусины после бисера: тип → цвета из списка (`black`, `crystal`, `pale`…). Типы — `ADDITIONAL_BEAD_TYPES`, цвета — `ADDITIONAL_BEAD_COLORS` в `scripts/data-rules.mjs`, переводы — `materials.additional_bead.*` и `materials.color.*` в `src/i18n/ui.ts`. На сайте цвет встроен в название: «Unbranded black bicones», «Basic pale beads»; брендовые (Preciosa, Swarovski) — жирным и с припиской: «**Preciosa crystal bicones** – fine Czech crystal». Ровно две — одной строкой: «Basic pale beads and unbranded crystal bicones». Названия и цвета переводятся.
- `threads` — нитки: тип → цвета как на катушке (`"Smoke"`, `"Crystal"`, `"#10"`), неизвестны — `[]`. Типы — `THREAD_TYPES` в `scripts/data-rules.mjs`, приписки — `materials.thread_note.*` в `src/i18n/ui.ts`. На сайте каждая нитка — отдельным пунктом; один цвет — в названии: «**FireLine Smoke** – ultra-strong American polyethylene thread», несколько — строкой «Colors: …».
- `findings` — фурнитура, своя у каждой категории (`npm run fill-data` вписывает нужный вид, редактор подсказывает по `category`):
  - брелок — одно из `CHARM_FINDINGS`: `Basic keyring` (keys), `Basic charm strap` (phone), `Large lobster clasp` (bag), `Basic hanging strap` (mirror). Подпись переводится;
  - серьги — строка текста как есть: `"Hypoallergenic stainless steel ear hooks"`;
  - браслет — детали `slideTubes` (или `beadEndings` — литые концевики Cymbal), `chain`, `adjustableChain`, `lobsterClasp`, `magneticClasp`, `connectorRings`; у каждой — бренд и металл из списка: `"Finrusiac rhodium-plated brass"`, `"Miyuki 24K gold-plated brass"`, `"Cymbal zamac"`, `"Basic stainless steel"`. Нет детали — пусто; фурнитуры нет совсем — всё пусто. На сайте — одно предложение, группы «бренд + металл» через «;»: «Zamac bead endings from **Cymbal**; rhodium-plated brass magnetic clasp from **Finrusiac**», «Basic **stainless steel** slide tubes, chain and connector rings». Бренд — жирным, без бренда жирным — металл. Соединительные колечки дописываются к деталям того же бренда и металла, а если таких нет — не выводятся. Варианты — `BRACELET_PARTS` и `METALS` в `scripts/data-rules.mjs`;
  - кольца и обмотки для ручек — поля нет, сборка упадёт, если оно есть.

Исход — один объект:

```json
"out": { "type": "sold", "date": "2026-09-03", "paid": 150000, "privateNote": "Купила девушка из кофейни напротив, сторговались" }
```

| Поле | Что это |
|---|---|
| `type` | `sold` — продана, `gift` — подарена, `lost` — брак или потеря, `kept` — оставили себе, в архив. Обязательно |
| `date` | Когда. Обязательно. Можно неполную дату (см. «Даты» ниже) |
| `paid` | Сколько реально получено, в донгах. Обязательно: у `sold` обычно равно `price` (меньше, если сторговались), у `gift`, `lost`, `kept` — `0` |
| `privateNote` | Комментарий к исходу: кто купил, кому подарили, что сломалось. На сайт не попадает |

Если в `out` заполнено хоть что-то, обязательны все три поля: `type`, `date`, `paid`. Пустой `out` — штука в наличии.

### Даты

`craftedAt`, `consignedAt` и `out.date` могут быть неполными — пишем столько, сколько известно:
- `2026-11-01` — точная дата;
- `2026-11` — только месяц: например, NGÀY MAI сообщает продажи за месяц без дат (пример в демо — HPPW04 в Happy Paws);
- `2026-Q3` — квартал: `Q1` — январь–март, `Q2` — апрель–июнь, `Q3` — июль–сентябрь, `Q4` — октябрь–декабрь (пример в демо — HPPW01 в Happy Paws);
- `2026-H2` — полугодие: `H1` — январь–июнь, `H2` — июль–декабрь (пример в демо — PPLG02 в Apple Grove);
- `2024` — только год: для старых записей (пример в демо — BWTC01 в Bowtie Cat).

`Q` и `H` — заглавные латинские, год всегда впереди: `2026-Q3`, а не `Q3 2026`. Тогда даты сортируются как обычный текст. Времён года нет: зима переходит через Новый год, а в Далате вместо них сезоны дождей и сухой. «Летом» — это `Q3`.

Несуществующие даты (`2026-13`, `2026-02-30`, `2026-Q5`, `2026-H3`) роняют сборку.

### Цена

**Политика магазина: цена везде и для всех одна** — в мастерской, у партнёров и на ремейк. Захотели поднять цену ремейка — поднимите её и у всех штук в наличии.

Цена на сайте (шапка товара, каталог, плашка семейства, ремейк) — одна, и считается только по тому, что есть сейчас:

1. **Есть штуки в наличии** (где угодно: Далат, NGÀY MAI, Cat Food) — их `price`. Цены у всех штук в наличии обязаны совпадать, а `remake.price`, если вписана, — быть равной им.
2. **В наличии ничего нет** — `remake.price`, и тогда она обязательна. Продали последнюю штуку — сборка попросит вписать цену ремейка.

Цены ушедших штук (проданных, подаренных, оставленных себе) на цену сайта не влияют — это история для накладных и отчётов, поэтому `price` у штуки обязательна и остаётся после ухода.

**Что видит сайт:**
- Готовых в мастерской нет — кнопка ремейка и комментарий из `remake.publicNote`; доставка, курьер и самовывоз из мастерской показываются всегда.

Код NGÀY MAI в данных не храним: он определяется по цене штуки (`getNgayMaiCategory`).

### Семейство — `data/_system/families/<id>.json`

Товары, которые показываются плашками-ссылками под галереей на странице каждого из них.

- `title` — заголовок над плашками, обязателен, с переводами.
- `members` — товары по порядку. У каждого необязательный `publicNote` — чем отличается, два-три слова («Крупный бисер»): выводится в плашке после цены.
- Товары с `"site": false` в семействе просто не показываются. На сайт семейство попадает, когда в нём хотя бы два товара с сайта: пока остальные не готовы, можно завести семейство из одного. Неизвестный товар или товар в двух семействах роняют сборку.

## Сборка и публикация

Сайт собирается только на этом компьютере: база изделий в Dropbox видна только здесь. GitHub Actions сайт не собирает.

- `npm run dev:restart` — перезапуск dev-сервера с чистым кэшем контента. Нужен после правок схемы (`src/content.config.ts`) и переименования полей: иначе страницы товаров отдают 404 или падают. Запущенный из скрипта сервер работает в фоне: `npx astro dev status | logs | stop`.
- `npm run build` — сборка в `dist/`. В конце — размер сборки, из чего она состоит, прирост с прошлой сборки и самые тяжёлые файлы. Лимиты GitHub Pages: сайт до 1 ГБ (предупреждение с 80%), файл до 100 МБ.
- `npm run deploy` — сборка и публикация: `dist/` уходит в ветку `gh-pages` одним коммитом с force push, история ветки не копится. Незакоммиченный код тоже публикуется (с предупреждением), в сообщении коммита — хеш исходного коммита.
- GitHub: Settings → Pages → Build and deployment → Source: **Deploy from a branch**, ветка `gh-pages`, папка `/ (root)`.
- `public/CNAME` — домен. Без него при публикации из ветки GitHub сбросит свой домен.

## QR-коды в модалках заказа

Лежат в `public/images/qr/` (`telegram.svg`, `messenger.svg`, `zalo.svg`), выводятся в `src/components/QrModal/`.

Генерируем здесь: https://www.nayuki.io/page/qr-code-generator-library

1. **Text** — полная ссылка с `https://`, например `https://m.me/bunnybearbeads`.
2. **Error correction** — Quartile.
3. **Output format** — Vector.
4. **Border** — 0.
5. Остальное не менять. Скачать SVG и положить в `public/images/qr/`.

После скачивания открыть SVG в редакторе:

- **Обязательно удалить белый фон** — строку `<rect width="100%" height="100%" fill="#FFFFFF"/>`. QR в модалке работает как маска: градиентом закрашивается всё непрозрачное, и с фоном вместо кода получится сплошной цветной квадрат.
- В тег `<svg>` добавить `width="500" height="500" shape-rendering="crispEdges"` — размер как у остальных и чёткие края клеток.

Проверить телефоном прямо из модалки на сайте, а не из самого файла: в файле код читается и с фоном.

## Большие скругления

При радиусе от 28px добавлять `corner-shape: superellipse(1.3);`:

```css
border-radius: 44px;
corner-shape: superellipse(1.3);
```

- Чтобы угол выглядел так же, как обычный круглый, радиус увеличить примерно в 1,2 раза (37px → 44px).
- При радиусах 12–16px разницы не видно — не добавлять. Кнопки, «пилюли» и круги не трогать.
- На мобильном (`width < 740px`) радиус меньше: у `.window` 28px вместо 44px.
- `@supports` не нужен: где поддержки нет, будет обычный круглый угол.

## Правила CSS

- **Цвета:** `rgb(255 255 255 / 90%)`, а не `rgba(255, 255, 255, 0.9)`; так же `hsl(h s% l% / a)`, а не `hsla()`.
- **Прозрачность** в процентах: `opacity: 80%`, а не `0.8`.
- **Медиазапросы** диапазонами: `@media (1600px <= width)`, `@media (width < 740px)`, `@media (740px <= width < 1200px)` вместо `min-width` / `max-width`.
- **Трансформации и раскладка:** где уместно — отдельные `translate`, `rotate`, `scale`, а также subgrid и логические свойства.
- **Переходы при наведении:** `var(--transition-hover)`, а не `0.2s ease`.

### Мониторы (`1600px <= width`)

Сайт не увеличиваем как при зуме: единого коэффициента нет, у разных свойств он свой.

| Что | Примерно |
|---|---|
| Шрифты, `line-height`, иконки | ×1,1–1,15 |
| Ширины, картинки, кнопки | ×1,13–1,2 |
| Отступы (`padding`, `margin`, `gap`) | ×1,2–1,3 |

- Это ориентир по уже свёрстанным компонентам, а не формула: итог подбираем на глаз. Размеры целые.
- Учитываем форму экрана: мониторы бывают и вытянутые, и невысокие (1600×800), поэтому высоту увеличиваем осторожнее ширины.
- Стили для мониторов — блоком `@media (1600px <= width)` в конце файла компонента.
